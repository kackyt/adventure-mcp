# Escape Exploration Review

脱出・探索作品を、設計段階と完成後の両方で監査する。固定六動詞への適合だけでなく、探索面、発見フェーズ、依存の統合、再訪、アイテムの使い回しが十分な厚みを持つかを検査する。

設計・実装の正規契約は [escape_exploration_gimmicks.md](../../ink-scenario-creator/references/escape_exploration_gimmicks.md) と [escape_exploration.md](../../ink-scenario-creator/references/genres/escape_exploration.md) にある。

## 1. 適用条件

次のいずれかなら Applicable とする。

- 脱出ゲーム、密室脱出、遺跡踏破、環境探索が主構造である。
- 見えている場所を調べ、道具や観察事実を組み合わせ、段階的にゲートを開く。
- ユーザーが脱出設計プレフライトを指定した。
- 既存作品へ、主要な脱出・探索ループを追加・改修する。

脱出・探索作品では、本レビューと [Fixed Command Harness Review](./fixed_command_harness_review.md) の両方を必須にする。六動詞へ従っていても探索構造が薄ければ本レビューで欠陥とし、探索量が多くても解決専用コマンドなら Fixed Command Harness で欠陥とする。

## 2. レビュー種別

開始時に次のどちらかを宣言する。

- **脱出設計プレフライト**：対象が脱出設計票、探索面マップ、依存グラフ、アイテム役割表、手がかりと錠の表、手数見積りであり、まだ Ink 実装前。
- **脱出完成品監査**：対象が実行可能な `.ink`、生成JSON、関連テスト、完成後の設計票とコールドプレイ記録を含む。

設計プレフライトでは、コンパイル、MCP実機、到達性を `NOT RUN（設計段階）` とし、それだけを欠陥にしない。設計票に実装後の検証計画が無い場合は指摘する。

設計者の口頭説明、後で足す予定、作者だけが知る解法で空欄を補わない。設計票または完成品に実際に書かれた証拠だけを使う。

## 3. 脱出設計プレフライト

### 3.1 規模プリセット

最初に実測表を作る。

| 項目 | 設計値 | 下限 | 判定 |
|---|---:|---:|---|
| 目標時間 | | 小10〜15分／中25〜45分／大60分以上 | |
| 発見フェーズ | | 小2／中3／大4以上 | |
| 安定視点 | | 小3／中5／大8以上 | |
| 見えるランドマーク | | 中14以上 | |
| 二段目の調査部位 | | 中8以上 | |
| 所持品 | | 中6〜10個 | |
| 同時所持ピーク | | 中4個以上 | |
| 主要ゲート | | 小2〜3／中4〜6／大7以上 | |
| 意味のある操作 | | 小20／中40／大70手以上 | |
| 以前の視点への再訪 | | 中2回以上 | |

数値は水増し目標ではない。下限未満でも、コールドプレイ相当の根拠から同等以上の厚みを説明し、調整理由を記録していれば個別判定できる。理由のない不足、または数だけ満たした置物は不合格候補とする。

### 3.2 探索面マップ

各場所・安定視点について次を確認する。

| 場所・視点 | 最初から見えるランドマーク | 調査後に現れる部位 | 得る事実・物・操作対象 | 解禁フェーズ | 再訪時の差分 | 判定 |
|---|---|---|---|---|---|---|

PASS条件：

- 場面本文から最初のランドマークが分かる。
- `しらべる → ランドマーク → 部位` の段階が設計されている。
- 必須対象が未提示名詞の自由入力に依存しない。
- すべてが最初の一巡でそろわず、フェーズ進行で古い場所の意味が変わる。
- 調査済み領域を再確認したとき、取得跡、状態差分、調べ尽くした範囲が分かる。

巨大な対象一覧を最初から出すことは段階探索の代替にならない。

### 3.3 依存グラフ

`観察 → 手がかり／物 → 別の場所での操作 → 新しい発見` を有向グラフとして監査する。

| 観点 | 設計値・経路 | 判定 |
|---|---|---|
| 最長依存列 | | |
| 同時に追える探索線 | | |
| 探索線の統合点 | | |
| 以前の場所へ戻る辺 | | |
| 発見フェーズの境界 | | |
| 単一ゲートへの集中 | | |

次をFAIL候補とする。

- 一本道の鍵→扉だけで全体が構成される。
- 並行探索線がなく、常に次の一手が一つしかない。
- 複数線が最後まで独立し、統合されない。
- 後の発見を受けて以前の場所へ戻る辺がない。
- 主要発見が最初の一巡で全部そろう。

### 3.4 アイテム×対象マトリクス

各所持品を、発見場所、使用場所、距離、組み合わせ、誤使用反応まで監査する。

| 所持品 | 発見場所 | 正用途の対象 | 取得から使用までの距離 | 別情報との統合 | もっともらしい誤使用先 | 誤使用反応 | 再利用 | 判定 |
|---|---|---|---:|---|---|---|---|---|

確認点：

- 入手した瞬間に用途が一つへ即断できないか。
- 一対一の鍵だけを並べていないか。
- 別々の場所で得た情報または物を統合する所持品があるか。中規模では少なくとも2個を目安にする。
- 再利用、物同士の組み合わせ、環境変化後の使用が混ざるか。
- 必須でない物にも、世界観、別解検証、ヒント、収集のいずれかの役割があるか。
- 誤使用が完全な無反応やGM採点でなく、形、距離、材質、機構等の反応を返すか。
- 誤使用で必須品を失わないか。

### 3.5 手がかりと錠

| 主要ゲート | 必要な観察事実 | 事実を得る場所 | 統合して導く内容 | 実演コマンド経路 | 正解文の露出 | 判定 |
|---|---|---|---|---|---|---|

- コード、順序、組み合わせは、原則として離れた2地点以上の観察事実を統合して導く。
- 手がかり本文は事実を示すが、正解値、正しい道具、操作順を完成文で言わない。
- 入力装置は、観察、装置の有効化、入力操作を別の六動詞経路で表す。
- 正解順序を選択肢ラベルへ書かない。
- 知識フラグ後に完成済み解法コマンドを出さない。詳細は Fixed Command Harness で照合する。

### 3.6 意味のある操作

手数は、解を知っている最短ルートではなく、手がかりを順に得る想定初見ルートで数える。

数える：

- 新規観察
- 状態変化
- 取得、使用、組み合わせ
- 推論を試す操作
- 新規または再文脈化された視点への移動

数えない：

- メニューを開く、戻る
- 既知の同文反復
- 無意味な往復
- 定型的な空振りの繰り返し
- 同じ結果へ至るためだけに分割したクリック

| フェーズ | 想定初見ルート | 最短ルート | 差の理由 | 水増しを除いた手数 | 判定 |
|---|---:|---:|---|---:|---|

想定初見ルートと最短ルートの差が、観察と推論から生じているかを見る。無意味な迷路移動や同文反復で差を作っている場合はFAILとする。

### 3.7 回復可能性と公開境界

| 失敗 | 状態変化 | 物理反応 | 再試行経路 | 必須品の保持 | 判定 |
|---|---|---|---|---|---|

次を確認する。

- 誤使用、誤順序、誤入力から必ず再試行できる。
- 移動、再調査、操作、戻るは sticky である。
- once-only は取得など本当に一度しか成立しない行動に限る。
- 一時的な映像・音の手がかりを再確認または記録できる。
- `public_status` は原則 `place` だけで、所持品、発見、解錠、段階、正解値を公開しない。
- 所持品と既知の観察事実は `もちもの` の authored text で確認できる。
- `RANDOM()`、shuffle、外部 Web、GMの独自状態へ進行が依存しない。

### 3.8 偽ボリューム監査

次を個別に判定する。

| 類型 | 該当箇所 | 影響 | 判定 |
|---|---|---|---|
| 数だけ多い置物 | | | |
| 単純 key-lock の反復 | | | |
| 定型的な「何もない」 | | | |
| 一対一で用途即断 | | | |
| 手がかりと錠が隣接 | | | |
| 同じ操作の反復 | | | |
| 無意味な往復 | | | |
| 最初の一巡で全発見 | | | |

数値下限を満たしていても、主構造がこれらで占められるならMajor候補とする。

## 4. READY判定

### Blocker

- 必須対象が名詞当てまたは作者だけが知るクリック位置に依存する。
- 主構造を固定六動詞＋outcome-gatingで表す計画がない。
- 必須品の不可逆消費、戻れない経路、選択肢ゼロ等の重大ソフトロックが設計にある。
- 正解値、正解順序、完成済み解法を本文・選択肢・入力要求へ露出する。
- 解決可能性を外部 Web の可変情報、乱数、GMの推測へ依存させる。

### Major

- 規模を名乗る根拠となる探索面、依存、手数が大きく不足する。
- 一巡で主要対象、所持品、手がかりがほぼ全部そろう。
- 主進行が単純 key-lock、置物、同文反復で水増しされている。
- 並行探索線、統合点、再訪のいずれかが主要規模に対して欠ける。
- 所持品の用途が一対一で、入手時に使い先を即断できる。
- 主要なコード、順序、組み合わせが複数地点の観察事実を統合しない。
- 誤使用、誤順序、誤入力からの復帰計画がない。
- `public_status` が所持、発見、段階、正解値を露出する計画である。

### Moderate

- 局所的に再調査描写が同文反復になる。
- 誤使用反応が弱く、次の試行を診断しにくい。
- 任意アイテムの役割が薄い。
- 想定初見ルートの一部が無意味な往復に頼る。

BlockerまたはMajorが一つでもあれば `NOT READY`。なければ `READY` とする。点数や長所でハードゲート違反を相殺しない。

## 6. 脱出完成品監査

完成後は、設計票の予定値でなく、実際の Ink、生成JSON、スモーク、MCP出力、コールドプレイ記録から再計測する。

### 6.1 設計票との差分

| 項目 | 設計値 | 実装値 | コールドプレイ実測 | 差分理由 | 判定 |
|---|---:|---:|---:|---|---|
| プレイ時間 | | | | | |
| 発見フェーズ | | | | | |
| 安定視点 | | | | | |
| ランドマーク | | | | | |
| 二段目の部位 | | | | | |
| 所持品 | | | | | |
| 同時所持ピーク | | | | | |
| 主要ゲート | | | | | |
| 意味のある操作 | | | | | |
| 再訪 | | | | | |

設計値を満たしたと自己申告するだけではPASSにしない。実際の選択肢と到達状態から数える。

### 6.2 コマンドと発見順

- 各到達状態のトップレベルが六動詞の順序付き部分集合か。
- 親ランドマークを調べる前に隠れた部位や物が出ないか。
- 露出前の物が `とる` に出ないか。
- 取得後に再取得できず、親の再調査結果が状態に合うか。
- 前提の前後で同じ `つかう`／`おす・うごかす` 経路が残るか。
- 解法文、正解順序、正解値が本文、選択肢、入力要求へ漏れていないか。

### 6.3 到達性と回復

- 標準クリアルートが実行できる。
- 誤った道具、ミスリード、誤順序、誤入力後もクリアルートへ戻れる。
- 移動、再調査、再試行が消えない。
- 非終端で選択肢ゼロにならない。
- 意味状態で重複排除した探索により、脱出不能状態や制御不能な状態爆発がない。
- 同じコマンド列を二回実行したとき、本文、選択肢、公開状態、終端が一致する。

### 6.4 公開状態

代表的な序盤、中盤、終盤で確認する。

| 時点 | `scene` | `choices` | `status` のキー | 非公開情報の漏れ | 判定 |
|---|---|---|---|---|---|

原則は `status.place` だけである。`public_status` 自体、所持品、`has_*`、`found_*`、解錠、段階、正解値が現れた場合は欠陥候補とする。

### 6.5 コールドプレイ

解を知らない別コンテキストで最低2回行い、次を記録する。

| 回 | 時間 | 意味のある操作 | 調べた対象数 | 同時所持ピーク | 再訪 | 詰まり位置 | 未使用品 | ヒント段階 | 総当たり |
|---|---:|---:|---:|---:|---:|---|---|---|---|

次を区別する。

- 発想や統合が難しくて詰まった。
- 操作できる対象が分からず詰まった。
- 必要な事実を再確認できず詰まった。
- 用途を即断でき、探索せず進めた。
- 総当たりの方が観察より速かった。

操作対象が分からない詰まりは、難易度ではなく選択肢階層または描写の欠陥である。中央値が目標尺や手数下限を下回る場合は、置物を足さず、依存フェーズ、統合、再訪を増やして設計から見直す。

## 7. 完成品監査の必須成果物

1. 適用パック表。Escape ExplorationとFixed Command HarnessをともにApplicableとする根拠。
2. 設計値、実装値、コールドプレイ値の比較表。
3. 探索面マップと、フェーズごとの新規発見。
4. 依存グラフの最長列、並行探索線、統合点、再訪辺。
5. アイテム×対象マトリクスと誤使用反応。
6. 手がかりと錠の統合表。
7. 想定初見ルートと最短ルートの意味ある手数。
8. 偽ボリューム監査。
9. ソフトロック、答え漏れ、公開境界の検証表。
10. コールドプレイ結果。

主構造が薄い場合は、固定コマンド違反とは別の Major／Blocker候補として報告する。
