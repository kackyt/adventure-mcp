# 謎解き要素の設計（adventure-mcp）

「お使い」ではなく**プレイヤーが推理して解く謎**を、状態秘匿アーキテクチャを壊さずに作るための定義・パターン・難易度レバー。

> 難易度モデルの2軸・合成則（加算 vs 乗算）・ジャンル別カタログ（嘘つき論理／アリバイ崩し／水平思考／換字暗号／論理グリッド 等）と対応 PoC の一覧は、総合リファレンス `docs/06-reference/PUZZLE_DESIGN.md` を参照。本書はその要約と Ink 実装の手引き。

> **最優先原則**: 「答えを N 択で選ぶゲーム」にしないこと。アドベンチャーの核は、世界をいじり試行錯誤しながら手がかりを見つける**過程**にある。解は「宣言」でなく**世界への働きかけで実演**させる（証拠を相手に突きつける／仕掛けを操作する）。どのジャンルでもこの探索の手応えを失わない。詳細は `docs/06-reference/PUZZLE_DESIGN.md` §0。

## 1. 「謎」の操作的定義（謎 ≠ お使い）

ある仕掛けが「謎」であるためには、次の3条件を**すべて**満たす。

1. **複数要素の統合 or 非自明な順序**
   単一行動では解けず、2つ以上の別々に発見する手がかり/アイテムの組み合わせ、または非自明な手順を要する。
2. **ノンスポイラー**
   正解の選択肢ラベル自体が答えを明かさない（後述の (B)(C) で実現）。
3. **失敗可能かつフェア**
   素朴に進むと解けず足踏み・別ルートになり得るが、提示済みの手がかりから**論理的に解ける**（理不尽な総当たり強制をしない）。

### 反例と正例（同梱サンプル）

| ファイル | 区分 | 理由 |
| --- | --- | --- |
| `docs/06-reference/scenarios/room_escape.ink` | ❌ お使い | 引き出しを調べれば鍵が手に入り扉が開く。推理も失敗もない（条件1・3を満たさない）。 |
| `docs/06-reference/scenarios/sages_tower.ink` のリドル | ❌ 総当たり可 | 答え（松明/太陽/灯火）を選択肢に並べており、条件2（ノンスポイラー）を満たさない。 |
| `docs/06-reference/scenarios/frozen_key.ink` | ✅ 謎（簡単） | 別々に得た松明＋油を「油→点火」の順で使う。答えはラベルに書かれない。素手/松明のみは失敗。 |
| `docs/06-reference/scenarios/frozen_key_normal.ink` | ✅ 謎（普通） | 上記に探索・条件充足・ミスリード・バッドエンド分岐を足してレバーを一段上げた版。 |

## 2. ノンスポイラーのコアモデル

選択肢メニュー＋状態秘匿＋サーバ側バリデーションという制約下では、**答えを選択肢に並べた瞬間にネタバレ（総当たり可能）**になる。これを避けるモデルは (A)(B)(C) の 3 つ。(B)(C) が基本で、(A) は「散らばった手がかりを統合して最後に解答を提出する」経路として使う。

### (B) 創発パズル（組み合わせ・順序）

個々の選択肢はすべて正当な行動。謎の本体は「どの行動を・何を持って・どの順で」行うか。ラベルは答えを言わない。

```ink
// 「油をかける」「松明をかざす」は行動を述べるだけ。「氷を溶かす正解」とは書かない。
// 正解は "油 → 点火" の順序（松明だけでは火力不足）= プレイヤーが推理する。
+ {has_oil && not oil_applied && not ice_melted} [氷に油をかける]
    とろりとした油が氷塊の表面いっぱいに広がった。
    ~ oil_applied = true
    -> altar_room
+ {has_torch && not ice_melted} [松明をかざす]
    {
    - oil_applied:
        油に一気に引火し、氷は見る間に溶け落ちた。中から鍵が現れた。
        ~ ice_melted = true
    - else:
        炎は弱々しく、表面がわずかに濡れただけだ。もっと強い火が要る。   // フェアな失敗ヒント
    }
    -> altar_room
```

### (C) 手がかりゲート（条件付き出現）

正解の選択肢は、必要な手がかり/アイテムが揃うまで `{条件}` で**出現させない**。メニューに答えが漏れない。

```ink
// 「鍵を取る」は氷が溶けるまでメニューに現れない。
+ {ice_melted && not has_key} [現れた鍵を取る]
    溶けた水の中から、濡れた鍵を拾い上げた。
    ~ has_key = true
    -> altar_room
```

### (A) 完全一致の自由入力（暗証番号・合言葉・記号列）(#13)

答えを**プレイヤーに打ち込ませる**提出経路。選択肢に答え候補が並ばないため、列挙不能な答え空間＝最強の総当たり耐性になる。手がかりの散布は (B)(C) をそのまま使い、(A) は「最後の解答提出」だけを担う。

```ink
VAR safe_code = ""

=== safe ===
ダイヤルに手をかける。 # input: safe_code
+ [ダイヤルを合わせる] -> safe_check

=== safe_check ===
{ safe_code == "2691":
    カチリと音がして扉が開いた。 -> opened
- else:
    留め金は動かない。番号が違うようだ。 -> shop
}
```

作者が守る契約（破ると engine が実装ミスとして落とす）:

1. **タグ**: 入力を受け付ける停止点の本文行に `# input: <VAR名>`。変数は `VAR` 宣言済みの文字列変数（`VAR safe_code = ""`）。
2. **継続用選択肢はちょうど 1 つ**: タグ付き停止点には判定ノットへ divert する sticky 選択肢（`+`）を 1 つだけ置く。このラベルはプレイヤー/GM に表示されない（engine が「自由入力待ち」として choices を秘匿し、`submit_input` だけを前進経路にする）。
3. **判定は Ink 側の完全一致のみ**: `{ var == "正解値": ... }`。AI/エンジンは正誤を判断しない（「惜しいから正解扱い」を構造的に排除）。
4. **誤答はループか終端 ED**: 不正解は入力元や探索ハブへ divert し、ソフトロックにしない。
5. **正解値は半角・トリム済みで書く**: 入力値は engine が NFKC 正規化＋前後トリムしてから注入する（全角数字は半角化される）。
6. **ノンスポイラー**: 正解値そのものを本文・選択肢に書かない。手がかりの統合（(B)(C)）からのみ到達できるようにする。

対象は**完全一致で判定できる入力のみ**。曖昧な自然言語リドル（同義語・表記ゆれ判定）は採用しない。最小 PoC: `docs/06-reference/scenarios/code_lock_poc.ink`（時計店の金庫。手がかりゲート＋年号×読み替えの創発で 4 桁コードに到達）。**ライブ作品に自由入力を入れる場合は §5 のスモーク観点で自作テストを添える**（参照シナリオ集の PoC 自体はテスト対象外）。

> **暗号ギミックの最終入力に (A) を使う場合**は `cipher_gimmick.md` §7「選択肢スロット型 ↔ 自由入力型の使い分け」を参照。既定は選択肢スロット型（英字・記号暗号は字種の揺れが無く安全）、数字コードや結論の確定は自由入力型。同じ生成器 config からどちらでも出せる（`--emit ink` / `--emit ink-input`）。
>
> **非暗号のコードロック（暗証番号・合言葉）の手がかり散布ネタ**は [code_lock_ideas.md](./code_lock_ideas.md)（摩耗キー・テンキー軌跡・制約の交差・折句・語呂合わせ・操作音の証言・誤答の痕跡）。作品のトーン＆マナー・舞台への適合で候補を絞り、**同格なら乱数で選ぶ**（毎回同じ骨格に寄せない）。

## 3. 謎のアーキタイプ・カタログ

> **カタログは生成メニューでなく検証ルーブリック。** アーキタイプから先に選んで中身を着せると既視感になる（型を固定した瞬間それが新しい紋切り型になる）。謎の*中身*は具体的な世界・人間から導出し、このカタログは「フェアか・一意か・**先が読めない／見覚えがないか**」を点検する物差しとして使う（mystery.md「新しさは『処方』でなく『濾過』で出す」を参照）。

| アーキタイプ | 概要 | Ink パターンの要点 |
| --- | --- | --- |
| **アイテム使用（手がかり統合型）** | 複数アイテムを揃え/組み合わせて使う | アイテム所持フラグ or `LIST` で管理し、`{carries(x) && carries(y)}` で正解行動をゲート |
| **手順・順序（状態機械）** | 正しい順序を踏むと状態が進む | `LIST State = a, b, c` で遷移を表し、各遷移を `{state == a}` でゲート。順序はヒントから推理させる |
| **条件充足** | 複数の前提が揃って初めて道が開く | `{cond_a && cond_b} [扉を開ける]` のように複合条件でゲート |
| **探索・観察** | 手がかり/アイテム自体が隠れている | 「調べる」行動で初めて入手（`frozen_key_normal` の床石下の油）。単体では謎にならず他型と組み合わせる |

> 単純な key-lock（`room_escape` の「調べる→鍵→開ける」）は**謎に含めない**。手がかりの統合も非自明な順序もなく、定義の条件1・3を満たさないため。

### アイテム管理の指針

`LIST` ＋ `carries()` 関数方式（`sages_tower.ink` 参照）と、用途が少なければ真偽フラグ方式（`frozen_key.ink` 参照）のどちらでもよい。**自己ループする部屋の一度きり判定は訪問回数に頼らず明示フラグで行う**（`adventure_mcp_patterns.md` の落とし穴1を参照）。

## 4. 謎/分岐軸の難易度レバー（簡単 / 普通 / 難しい）

謎の"構造"は (B)(C) で共通のまま、次の4レバーで難易度を段階化する。

| レバー | 簡単 | 普通 | 難しい |
| --- | --- | --- | --- |
| **ヒント密度** | ほぼ答え（手厚い） | 事実のみ・要約1回 | 暗示のみ／自力推理 |
| **ミスリード(red herring)** | 0 | 1〜2 | 3以上 |
| **謎の数** | 1〜3 | 4〜7 | 8以上 |
| **分岐の深さ** | ほぼ一本道 | 2〜3層・バッドエンド1〜2 | 4層以上・複数エンディング |

> ボリューム・戦闘・ゲームオーバー/バッドエンドの各軸レバーは別途（難易度カタログ Issue #11）で扱う。ここでは謎/分岐軸のみ。

### レバーの上げ下げ：Ink 差分例

**ヒント密度（手厚い → 事実のみ）** — 結論を述べず、事実だけ提示して推理させる。

```ink
// 簡単: 答えに近い
+ [氷塊を調べる]
    かなり分厚い氷だ。生半可な熱では、とても溶けそうにない。     // "熱が要る" と明言

// 普通: 事実のみ
+ [氷塊を調べる]
    白く凍てついた厚い氷だ。叩くと硬く高い音が返ってくる。       // 結論は言わない
```

**ミスリード（0 → 1〜2）** — それらしい誤答を置く。ただしフェアに「効かない」と示し、進行不能にしない。

```ink
+ {has_hammer && not ice_melted} [金槌で氷を打ち砕く]
    渾身の一撃を叩き込む。だが氷は鈍く撥ね返すばかりで、罅ひとつ入らない。   // 物理は無効と明示
    -> ice_chamber   // 失敗だがデッドエンドにしない
```

**分岐の深さ（バッドエンドの追加）** — 選択で結末を分岐させる。バッドエンドも必ず終端ED（`-> DONE`/`-> END`）に繋ぎ、ソフトロックにしない。致死/取り返しのつかない分岐は**予兆を必ず描写**する。

```ink
=== ignite ===
広げた液体は思いのほか多い。勢いよくやれば早いが、跳ね返る炎が危うい。   // 予兆（フェア）
* [慎重に炙る]
    ~ ice_melted = true
    -> ice_chamber
* [一息に引火させる]
    跳ね返った炎に腕を焼かれてしまった。
    ~ ice_melted = true
    ~ burned = true   // 結末分岐用フラグ。後の ending で文面を変える
    -> ice_chamber
```

## 5. 検証（必須）

`pnpm run build:ink` のコンパイル成功だけでは実行時の破綻（デッドエンド・一度きりイベント再発・解けない謎）を検出できない。**生成 JSON を inkjs で実際に再生**し、最低限以下を確認する（BOM 除去 `replace(/^﻿/, "")` を忘れない）。

- 手がかりから正解ルートに到達でき、クリア（`-> DONE`/`-> END`）できる
- 素朴に進む「失敗ルート」が存在し、かつそこから挽回できる（デッドエンドにならない）
- バッドエンドがある場合、意図どおり発生し、それも終端ED（ソフトロックでない）
- 一度きりイベントが再訪で再発しない

参照シナリオ（`.ink` ソース）は `docs/06-reference/scenarios/` にある（参照資料・コンパイル対象外）。**新しいライブシナリオを `engine/assets/` に作るときは、上記をスモークプレイで検証するテストを必ず添えること。**

## 6. 帰納・融合・物語接地・失敗モード（難易度カタログ #11 の追加）

詳細は `docs/06-reference/PUZZLE_DESIGN.md`（§0.5・§3.7・§4）。本節はその要約。

### 6.1 新しい引き出し

- **帰納（隠れた法則の発見）** — PoC: `docs/06-reference/scenarios/oracle_runes.ink`。法則はどこにも明記せず、
  試行→観察で構築させる（探偵でなく科学者の推論）。**肝**: ゴールを「1つの正解配置を作る」に
  すると推測で通り帰納が飾りになる。**学んだ法則を"新しい複数ケース"に適用させる審判**
  （問題数 > 実験回数）で生成を強制する。
- **帰納×演繹の融合** — PoC: `docs/06-reference/scenarios/legendary_forge_cmd.ink`（固定コマンドパレット版・
  接地済み）。演繹（手記）で候補を2つに絞り、帰納（鱗片に試す＝銀だけ噛む）で最後を断つ。
  **どちらか片方では一意に到達しない**ことを、`演繹のみ=N候補／法則込み=一意`として
  スクリプトで機械検証してから実装する。
- **帰納×暗号（既知平文攻撃）** — 既知の平文↔暗号文ペアから暗号規則を帰納させ、本命を1文字ずつ綴らせる
  封印。方式（グロンスフェルト等）に固定しない**方式非依存の骨格・フェアネス・機械生成器**は
  [cipher_gimmick.md](./cipher_gimmick.md)。暗号文・スロット別ダミー・Ink 雛形・verify を生成器が計算する
  （**人手で暗号を解かない**）。実例＝machida 第2章（グロンスフェルト・鍵205）。
- **合成（グリフ／見立て）** — 千切れた部品を上下/左右に重ねると別の字になる（火＋火＝炎、山＋石＝岩）。
  可読性は漢字分解（IDS）＝人手検証済みの合成辞書に委ね、**合成はプレイヤーの脳内で・入力させず探し当て
  interact で回収**（§6.7 厳守）。骨格・断片の割り方・カモフラージュは [glyph_composition_gimmick.md](./glyph_composition_gimmick.md)。

### 6.2 物語接地（diegetic）：法則は世界から生やす

仕掛け・法則は**世界の理（物理・常識・設定）から必然として立ち上がる**こと。恣意的な
ゲーム都合にしない。失敗例 `apothecary_brew`（揮発と解錠が無関係＝「なぜ？」が残る）↔
正例 `legendary_forge_cmd`（銀の弱点・柄が要る・龍油で鈍る＝すべて世界の理）。
着想の源は「鍵を組み立てる／凶器の組み合わせ（銃と銃弾）／伝説の装備を鍛える」のように
**世界で何が機能するか**に法則を一致させる。

### 6.3 固定コマンドパレットで実演させる

謎は独自トグルUIや「答えを選ぶ」メニューでなく、**固定の動詞（しらべる→対象／つかう→
道具→対象／もちもの）＋ outcome-gating** で実演させる（`PUZZLE_DESIGN.md` §0・§6、
PoC: `escape_room.ink` / `legendary_forge_cmd.ink`）。解決専用コマンドを湧かせない。

**動詞は「どこに判断があるか」で選ぶ。** 手にある得物で殴るだけ（判断が"どれを使うか"に
無い）＝`たたく→対象`、どの道具を使うかが謎の核＝`つかう→道具→対象`。剣・素手は たたく、
マジックアイテム・鍵・消耗品は つかう。専用の戦闘・資源動詞を作ると「殴る／回復する」
連打モードが復活するので作らない（`adventure_command.ink` は たたく＝物理／つかう＝道具選択、で既に分離）。

**動詞語彙は全編で固定・場所で生やさない。** パレットの動詞（`しらべる／とる／たたく／
つかう／うごく／もちもの／はなす` 等）は最初から最後まで不変で、場所ごとに変わるのは
**対象（サブメニュー）だけ**。「排水する」「重ねる」「鍛える」「挑む」のような**その場限りの
専用動詞をトップに生やさない**——学習コストが上がりユーザーに不親切だから。ある動詞を
**対象の無い部屋で非表示にする**のは可（既知動詞の活性/非活性であって"新しい動詞"ではない）。
語彙を絞る基準は**「働きかけの種類に一致させる」**：同じ働きかけは畳む（`おす`→`たたく`＝
どちらも固定物に力を加える）、違う働きかけは分ける（`しらべる`＝検分して情報を得る／`とる`＝
携行品を取得。畳むと"調べられる＝取れる"の誤結合が生じ制約過多になる）。**数を減らすこと
自体が目的ではない**。

### 6.4 難易度づくりの失敗モード（潰すべき6つ）

機械的消去で解ける／鍵の"提示"で再認になる／反復で飽きる（またあれか）／最終が推測可能／
法則が恣意的／**難読な言い回しで難しさを偽る**（読みにくいだけで推論が要らない＝面倒で
あって謎でない）。共通核は **「再認/選択で済むものは易しい。生成（自分で着想・法則・統合を作る）を
強いる設計だけが難しい」**。

**手がかり（`しらべる` 等）は事実のみを平易に書き、答え・解法・「○○が効く」式の結論を
綴らない。** 難しさは言い回しの晦渋さでなく、平易な事実を繋ぐ推論から出す（`しらべる→彫り`＝
「刃と炎、二つの印が並んで彫られている」＝事実。○ / 「炉で鍛えれば倒せる」＝答え。✗）。

**ただしゲームの大目的は開幕で示す。** ストーリーも目的も示されないままフィールドに
放り出されると、プレイヤーは何をすればいいか分からない。開幕で「誰が・何のために来て・
どうなれば終わりか」を言い切る（例：星髄を採って生きて戻る）。これは**開幕の話**であって、
道中の障害ごとに「いま何を探すか」を逐一言い直すことではない——それは探索の答え探しを
先回りするネタバレに近づく。中間目標はプレイヤーが世界から読み取って自分で立てるもの。

**物語の「前提」と「謎」を混同して、前提のほうを隠さない。** 世界の成り立ち・なぜこう
なったか等の前提は、それを解き明かすことがプレイヤーの目的でない限り**開幕で語ってよい**
（むしろ断片で小出しにすると「発見」の報酬にならず、ただの説明不足に感じられる）。伏せて
発見させるのは、プレイヤーが能動的に解こうとしている謎（＝その解明が目的）と、その解法だけ。
判定基準：**それを解き明かすことがプレイヤーの目的か、別の目的のための背景か**。背景なら先に
明かす（前提を先に渡すほうが、道中の目標が明確になり、謎の解法は隠れたまま迷子だけが消える）。

### 6.5 AI は自分の破綻を検知できない

難易度も物語整合性も AI は自己採点しにくい（知識の呪い）。**全自動生成では、前提・動機・
"なぜその仕掛けが世界で成立するか"を人間が一読して弾く関所**を置く（SKILL.md の作成モード参照）。

### 6.6 豊かなボリューム・持続的難易度・物語進行の足場

詳細は `docs/06-reference/PUZZLE_DESIGN.md` §9。**ボリュームはノット数でなく「依存の深さ×
物語の節」で作る**（フラットな一発入手の山では尺は伸びない）。大ボリュームの目安：

- **段階フェーズ ≥3**（発見が次のエリア/人物/話題を解禁。全手がかりを一巡で取らせない）
- **各容疑者は2手以上で初めて白黒**（タダの除外を作らない＝消去法禁止）
- **サブ謎 ≥2**（ロック端末・暗号ログ等で進行をゲート）
- **進化する証言**（証拠提示・新事実で台詞/態度/開示が変わる。再尋問で新情報）
- **中盤の再フレーム ≥1**（疑っていた構図が覆るどんでん返し）
- **消去法に化けさせない**: 犯人を「最後の1人」にしない。仕立て上げを本気で（素朴な消去は
  偽犯人を指し、真犯人は正の推理でのみ届く設計に）。
- **尺の見積り＋拡張ループ**: 想定時間≒Σ(各フェーズの手数)。目標帯に満たなければフェーズ/
  サブ謎/進化証言/再フレームを足して反復。
- **大ボリューム×リッチ物語は共作推奨**（おまかせの天井。完成時は尺・厚み・非消去・物語
  進展を人間が確認する関所を通す）。

### 6.7 気づき型の謎：アハを選択肢で回収しない（合成・帰納・暗号の鉄則）

「気づき（合成・帰納・見立て）」を核にする謎で**最優先の原則**。破ると気づいた瞬間のアハ体験が丸ごと消える。

- **気づきはプレイヤーの頭で起こす。ゲームが代わりに解いて答えを印字しない。** 断片は素のまま見せてよい
  （手がかり＝答えではない）が、「重ねる／解読する」を一手で実行して**結果を表示する演出は禁**（＝カットシーン。
  プレイヤーは何も解いていない）。例：千切れた札は上下2枚を別々に見せるだけ。重ねて読むのはプレイヤーの脳内。
- **気づいた答えを"入力・選択"で問わない。** 合成後の字・語を選択肢に並べる／スロット入力させると
  **再認の N 択に堕ちる**。§2(A) の自由入力が使えるようになっても、**気づき型の核**（合成後の字・
  見立て・帰納した法則そのもの）を打ち込ませない——アハが検定に変わる。(A) が向くのは暗証番号・
  犯人名のような**結論の確定**であって、気づきの回収ではない。気づきの結果は**世界への行動で表現させる**：
  読み取った先を**探し当てて `しらべる`／`つかう`** で実演する（`固定コマンドパレット` §6.3）。
- **指す先は「固有名の既知地への移動」でなく「要素が描写する一点」にする。** 前者は場所縛りになりがちで、
  行き先ラベルが答えを漏らす。要素（例：高台・水際・白い石…）が**世界の具体的な一点**を描写し、
  プレイヤーがそこを**探し当てて interact** する形にすると、命名ゼロ・探索と地続き・メニューに答えが出ない。
- **カモフラージュを十分に置く（ごり押し防止）。** interact 型は、正解の一点を**凡庸な interact 候補の中に
  埋める**。候補が少ないと謎を解かず総当たり investigate で当たる。探索空間を広く取り、**手がかりで絞って
  初めて効率的に届く**ようにする。
- **空振り・メタ発言を置かない。** 外れた候補に「何も無い／惜しい」の空振りビートや、謎解きへの注釈・
  ほのめかし（メタ）を返さない。**各カモフラージュは独立した diegetic 内容を持ち、それ自体が本物として読める**。
  正解だけが、解いた文脈でのみ意味を結ぶ。「外れ」だと分かる signposting を出さない。
