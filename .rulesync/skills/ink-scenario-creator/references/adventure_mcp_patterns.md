# adventure-mcp プロジェクト固有の実装パターン

`adventure-mcp` プロジェクトにおけるシナリオ作成のベストプラクティスと制約事項です。

## 基本原則：状態管理の秘匿

AIエディタ（MCP）とシナリオエンジン（InkJS）は分離されています。AIは「ゲーム全体のシナリオ」や「未解明のフラグ」を事前に知ることはなく、現在プレイヤーがいる場所、見えているもの、実行可能なアクションのみを提供されます。

- **AIに考えさせない**: プレイヤーのステータス増減や、アイテム取得の判定、イベント進行のフラグ管理はすべて `.ink` ファイル内に記述します。AIに「アイテムを与えて」と指示するのではなく、Ink内で完結させてください。
- **堅牢な状態遷移**: シナリオ上の分岐は必ずInkの選択肢（Choices）として表現します。AIはテキストの提示と、ユーザーの意思決定に基づく選択肢の実行のみを仲介します。

## 公開ステータス変数 `public_status`

AI（ゲームマスター役）には未解明のフラグやネタバレを渡しませんが、HP・所持金・現在地のような「プレイヤーに常時見えていてよいステータス」だけは予約変数 `public_status` で**明示的に公開**します。生成する `.ink` には**必ず** `public_status` を含めてください。

### 書式

ファイル先頭で、固定名 `public_status` を**文字列**として宣言し、公開する変数名を**カンマ区切り**で列挙します。

```ink
VAR player_hp = 20
VAR gold = 0
VAR location = "entrance"
VAR has_master_key = false       // 解法フラグ：公開しない

// player_hp / gold / location のみ公開。has_master_key は含めない。
VAR public_status = "player_hp,gold,location"
```

- 変数名は `public_status` 固定（リネーム不可）。値は文字列。
- 列挙する名前は `VAR` 宣言済みの変数名と完全一致させ、余分な空白を入れない。
- 公開するものが無いシナリオでも `VAR public_status = ""` を必ず宣言する。
- `public_status` 変数自体と、列挙していない変数は AI／プレイヤーへの出力に含まれない（エンジンが除外）。AI に渡るのは列挙した各変数の現在値だけ。

### 見せる変数／隠す変数の判断基準

| 区分 | 例 | `public_status` に載せる？ |
| --- | --- | --- |
| 進行状況の指標 | `player_hp`, `gold`, `location`, `turn_count` | ○ 載せる |
| 解法・進行フラグ | `has_key`, `is_door_open`, `knows_culprit`（`has_*` / `is_*` / `knows_*` 系） | × 載せない |
| 真相・正解値 | `culprit_name`, `correct_code` | × 載せない |

判断に迷ったら「**この値をプレイヤー画面に常時表示しても謎の難易度が変わらないか？**」を基準にします。難易度が変わる＝ネタバレなので載せません。

## 自由入力モード `# input: <var>`（完全一致の解答提出）

暗証番号・合言葉・犯人名のような「選択肢に並べられない答え」をプレイヤーに打ち込ませるための予約タグです。タグを検出した engine は選択肢の代わりに「自由入力待ち」を返し、入力値を NFKC 正規化＋前後トリムして指定変数へ注入してから物語を再開します（ink 公式が推奨する「入力 UI はゲーム側・`variablesState` で注入」パターンの実装）。

### 書式と作者契約（破ると engine が実装ミスとして落とす）

```ink
VAR safe_code = ""

=== safe ===
ダイヤルに手をかける。 # input: safe_code
+ [ダイヤルを合わせる] -> safe_check

=== safe_check ===
{ safe_code == "2691":
    カチリと音がして扉が開いた。 -> opened
- else:
    留め金は動かない。番号が違うようだ。 -> shop
}
```

1. **タグは停止点の本文行に付ける**: `# input: <VAR名>`。変数は `VAR` 宣言済みの**文字列**変数（`VAR safe_code = ""`）。未宣言だと実行時エラーになります。
2. **継続用選択肢はちょうど 1 つ**: タグ付き停止点には、判定ノットへ divert する sticky 選択肢（`+`）を 1 つだけ置きます。ラベルはプレイヤー/GM に表示されません（engine が秘匿）。0 個や 2 個以上はエラー。
3. **正誤判定は Ink 側の完全一致のみ**: `{ var == "正解値": ... }`。AI/エンジンは正誤判断に関与しません。
4. **誤答はループか終端 ED へ divert**（ソフトロック禁止）。正誤判定ノットから元のハブへ戻せば再挑戦できます。
5. **正解値は半角・トリム済みで書く**: 全角入力は半角へ正規化されてから比較されます。
6. **正解値をノンスポイラーに保つ**: 本文・選択肢ラベルに正解値を書かない。`# input` の変数は `public_status` に載せない。

最小 PoC: `docs/06-reference/scenarios/code_lock_poc.ink`（設計論は `puzzle_design.md` §2(A) を参照）。

## 出力ファイルの構成と配置場所

- 作成したシナリオファイルは、常に `engine/assets/` ディレクトリ配下に `.ink` 形式で保存します。
- 保存後、プロジェクトルートまたは `engine/` ディレクトリにて `pnpm run build:ink` コマンドを実行し、コンパイルエラー（文法エラーや無効な参照など）がないことを確認してください。

## シナリオ記述のベストプラクティス

### 1. 状況の明確な描写
AIがゲームマスターとして振る舞うため、ノットの冒頭では「現在の状況、目に見えるもの」を明確に描写してください。

```ink
=== room_01 ===
あなたは薄暗い石造りの部屋にいる。
北には重い鉄の扉があり、部屋の中央には古い木箱が置かれている。
```

### 1.1 プレイヤー向け文章の読みやすさ（全ジャンル共通）

プレイヤーが読む文章は、原則として小学校高学年から中学生が辞書なしで読める言葉と文の長さにする。詳細な共通規範は [INK_GUIDE.md §4.4.1](../../../../docs/06-reference/INK_GUIDE.md) に従う。

1. **形・場所・動きを先に書く**：専門的な名前から始めず、何が見え、どこにあり、どう動くかを先に示す。
2. **短い呼び名へ統一する**：同じ物を別の熟語で何度も呼ばない。初出後は一つの短い名前を使う。
3. **未知の物を詰め込まない**：一文へ新しい人物・部品・制度・状態をいくつも入れず、観察と変化を短文へ分ける。
4. **必要な難語はその場で説明する**：固有名、歴史語、職業語を消す必要はないが、進行に必要なら普通の言葉で意味が分かるようにする。
5. **平易な事実と結論を分ける**：見えた跡、聞いた言葉、減った資源は分かりやすく書く。犯人、正解順序、正しい道具など、プレイヤーが導く結論は書かない。

#### 悪い例と良い例

```text
脱出・探索
悪い: 油圧ラムの作動圧が立たず、連結杆も未閉鎖だ。
良い: 水で動く棒は沈んだままだ。横のつなぎ棒にも、まだすき間がある。

推理
悪い: 裏口には汚泥の残痕があり、靴底の擦過痕のような存在が判明した。
良い: 裏口の泥に、かかとを引きずった靴跡がある。

サバイバル・RPG
悪い: 継戦資源の枯渇により戦闘続行は困難だ。
良い: 薬はあと一つ。傷も深く、次の戦いは危ない。

物語分岐
悪い: 組織内調整を優先し、関係修復のための意思表明を保留する。
良い: 今は仲間へ返事をせず、先に上司と話す。

キャラクター
悪い：坑鼠
良い：大ねずみ
```

良い例は状況を理解しやすくするだけで、正解や最善手を決めていない。簡単な言葉へ直すときも、別々の手がかりを一つの答えへまとめたり、選択肢へ完成済みの解法を書いたりしない。

### 2. 選択肢は行動として提示
プレイヤーの取り得る行動を明確な選択肢として列挙します。一度しか実行できないアクション（宝箱を開ける等）には `*` を、何度でも実行できるアクション（調べる等）には `+` を使用します。

```ink
+ [周囲を調べる]
    壁には古い松明がかけられているが、火は点いていない。
    -> room_01
* [宝箱を開ける]
    宝箱には鍵がかかっておらず、中から古びた鍵を見つけた。
    ~ has_key = true
    -> room_01
```

### 2.1 プレイヤーの状態とNPC台詞を同期する

NPCの反応や台詞は、プレイヤーが実行した行動と獲得した知識のフラグに合わせる。まだ入手していない情報をNPCが前提にしたり、解決済みの事件へ初回と同じ反応を返したりしないよう条件分岐する。

- 知識・発見・関係の変化は明示的なフラグで管理する
- 一度きりの反応は訪問回数に頼らず真偽フラグで管理する
- 選択肢を消す必要がなければ、同じ行動への**結果や台詞を変える**ことで状態変化を見せる
- 自由な攻略順がある場合は、各台詞が必要とする前提フラグを設計時に列挙し、未取得情報への言及がない経路もテストする

### 2.2 表示単位（ページ／シーン）の停止点

adventure-mcp の `GameSession` は、Ink が選択肢・`# input:`・`END`／`DONE`へ達するまで `continue()` を繰り返し、途中の本文を一つの `scene` に結合する。**ノット、ステッチ、`->` divert、空行は表示境界ではない。**

```ink
=== page_a ===
一つ目の文章。
-> page_b

=== page_b ===
二つ目の文章。
+ [しらべる] -> examine
```

上記は「一つ目の文章。」「二つ目の文章。」が同じ `scene` に表示され、その後に `しらべる` が出る。

次の本文をプレイヤーの確認前に見せない意図的な区切りでは、表示制御用の停止選択肢を置く。

```ink
=== chapter_1_end ===
——第一章 了——
まだ、答えは出ない。
+ [つぎへ] -> chapter_2_intro

=== chapter_2_intro ===
翌朝。雨は上がっていた。
-> chapter_2_hub

=== chapter_2_hub ===
+ [しらべる] -> examine
+ [はなす] -> talk
```

固定コマンド作品では、**行動結果から本文ありの場所／sceneへ入り直す箇所**も表示境界である。同じ場所へ戻る場合でも、結果文の直後に場所の導入・状態説明をもう一度出すなら、停止なしの divert にしない。

悪い例：

```ink
=== try_locked_door ===
大きな戸が道をふさいでいる。
-> room_hub

=== room_hub ===
海側の部屋。窓と大きな戸がある。
+ [しらべる] -> look_menu
+ [ばしょいどう] -> travel_menu
```

この場合、失敗文と「海側の部屋……」が同じ `scene` に連結される。

正しい例：

```ink
=== try_locked_door ===
大きな戸が道をふさいでいる。
+ [つぎへ] -> room_hub
```

結果から戻る場所を `place` で選ぶ場合は、共通停止ノットにまとめてもよい。

```ink
=== result_to_place ===
+ [つぎへ] -> return_to_place
```

一方、次は追加のページ停止を置かない。

```ink
=== inspect_door ===
戸には鍵がかかっている。
-> inspect_menu

=== inspect_menu ===
何をしらべる？
+ [戸] -> inspect_door
+ [やめる] -> room_hub
```

`inspect_menu` が出すのは場所の再導入ではなく、同じ操作内の短い対象質問である。また、通常移動の行き先や `やめる` を選んだ直後は、その選択自体が停止点であり、途中に結果本文を挟まないなら移動先／現在地の本文をそのまま出してよい。

`つぎへ` の契約：

- 無条件の sticky choice `+ [つぎへ] -> next` を標準形とする
- 純粋なページ停止点では原則1択にし、固定コマンドパレットと同じ一覧へ混ぜない
- 固定パレットのゲーム内動詞ではなく、**表示制御専用の例外**として扱う
- 意味のある分岐がすでにある場面では、その分岐自体が停止点なので追加しない
- 謎・移動・戦闘のゲートを `つぎへ` で代用しない
- セーブ／ロードや再入場で選択肢が消えないよう、ページ送りには原則 `*` を使わない

`つぎへ` が必要になりやすい箇所：

- 章末から次章
- 幕間・回想・タイトルカード
- 視点・主人公・時刻の切り替え
- 複数ページに分けるプロローグ／エンディング
- 次の文章前に余韻や確認を置く箇所
- 移動ゲート、操作、道具使用、取得、持ち物表示、入力結果などの本文から、導入・状態説明を出す場所／sceneへ入り直す箇所

置かない箇所：

- 同じ場面の連続した段落・会話
- 実装上ノットを分けただけの連続文
- 調査結果から、本文を持たないメニューまたは短い対象質問へ戻る divert
- 場所の導入文から、本文を持たない固定コマンドハブへ進む divert
- 結果本文を挟まない通常移動・メニューキャンセル
- `# input:`、意味のある選択肢、`END`／`DONE`ですでに停止する箇所

スモークプレイでは、実際の MCP `scene`／`choices` を使い、(1) 結果ページに次の場所固有の導入・状態説明が含まれない、(2) `choices` が原則 `つぎへ` の1件、(3) 選択後に場所本文と次の意味ある選択肢が出る、の三段階を検証する。移動ゲートの成功・失敗、操作、正誤の道具使用、組み合わせ、取得、持ち物表示、入力結果から代表経路を選ぶ。通常移動・キャンセル・本文なしメニュー復帰に冗長な `つぎへ` がないことも確認する。構文だけから作者の表示意図は判定できないため、すべての divert を静的lintで禁止しない。

### 3. デッドエンド（行き止まり）の回避
シナリオ内でプレイヤーが選択肢を失い、進行不能になる状態（デッドエンド）を避けるため、ノットの最後には必ず選択肢を配置するか、別のノットへ遷移（`->`）するか、あるいはシナリオ終了（`-> DONE`）を明記してください。

### 4. フォールバック選択肢（Fallback Choices）
状況が変化した際に、何も選択できるアクションがなくなってしまうことを防ぐため、条件なしのフォールバック選択肢を用意することが有効な場合があります。

```ink
* [調べる] -> investigate
* [休む] -> rest
+ ->
    （これ以上できることはないようだ…）
    -> DONE
```

## InkJS / CLI 検証で踏んだ落とし穴（実証済み）

`engine`（inkjs 2.x）でのコンパイル・実機プレイで実際に遭遇した不具合とその回避策です。新規シナリオでも繰り返し踏みやすいので必ず確認してください。

### 1. 同一ノットへの自己 divert では訪問回数が増えない
「部屋にとどまってアクションを繰り返す」ループを `-> same_knot` で実装すると、**そのノットの訪問回数（`{knot}` / `CNT?`）が再入場で増えません**（inkjs の既知の癖。`docs/06-reference/inkfiles/builtins/visit_count_bug_due_to_nested_containers.ink` 相当）。

そのため「初回だけ戦闘」「初回だけの描写」を `{ knot == 1: ... }` で制御すると、再訪のたびに再発します。

- **対策**: 自己ループする部屋の一度きりイベントは、訪問回数ではなく **明示的な真偽フラグ**で管理する。

```ink
VAR goblin_beaten = false
=== floor_2 ===
{ not goblin_beaten:
    -> combat ->
    ~ goblin_beaten = true
}
// 選択肢で -> floor_2 にループしても再発しない
```

訪問回数・gather 読み取り回数が確実に効くのは、**外部から毎回入り直すノット**（tunnel 呼び出し・thread・別ノットからの divert）や **gather ラベル**に対してです。

### 2. 選択肢リストの中に入れ子選択肢を直書きしない
ノット直下の選択肢（`*` / `+`）の配下に、さらにインデントして入れ子の選択肢を書くと、weave のギャザー構造が壊れ、再入場時に実行時エラー **「ran out of content. Do you need a '-> DONE' or '-> END'?」** が出ることがあります。

- **対策**: 入れ子の分岐は**独立したノットに切り出して `->` で飛ばす**（プロジェクト指針の「分岐はノットで」とも合致）。

```ink
// NG: floor_1 の選択肢リスト内に入れ子を直書き
+ [井戸を覗く]
    * [縄で降りる] -> floor_1
    * [素手で降りる] -> game_over

// OK: 独立ノットに切り出す
+ [井戸を覗く] -> well
=== well ===
* {carries(rope)} [縄で降りる] -> floor_1
* [素手で降りる] -> game_over
+ [やめておく] -> floor_1
```

### 3. インライン条件は「2分岐まで」かつ代入（`~`）を含められない
`{ cond: A | B }` のインライン条件は分岐が**最大2つ**まで。3分岐以上の出し分けや switch は**複数行ブロック**で書きます。また `{ cond: ~ var = x }` のようにインライン条件内へ `~` の代入文は置けません（コンパイルエラー）。

```ink
// 3分岐以上 / 代入を伴う条件は複数行で
{
- gate == sealed: 扉は封印されている。
- gate == runed:  ルーンが光っている。
- else:           扉は開いている。
}
{ hp <= 0:
    ~ death_cause = "sage"
    -> game_over
}
```

### 4. 移動・再入場の選択肢は sticky（`+`）にする
フロア間移動や「もう一度話す」など**繰り返し選べるべき選択肢を once-only（`*`）にすると、一度使った時点で消えてデッドエンド化**します（例: 一階に戻ると「上の階へ」が消える）。アイテム取得や一方向の状態遷移だけ `*`、移動・再入場系は `+` を使い分けてください。

### 5. tunnel 復帰後は「成功」と「中断（逃走）」をフラグで区別する
tunnel（`-> combat ->`）は勝利でも逃走（`->->`）でも同じ場所に戻るため、戻り先で結果を判別できません。撃破フラグを戦闘ノット末尾で一律に立てると「逃げても撃破扱い」になり、報酬や再戦の整合が崩れます。

- **対策**: 勝利時のみ立てるフラグ（例 `last_battle_won`）を戦闘の `win` gather 内でセットし、呼び出し側でそれを見て分岐する。

### 検証手順の推奨
`pnpm run build:ink` のコンパイル成功だけでは実行時エラー（上記 1・2 など）は検出できません。**生成 JSON を inkjs で実際に再生し**、一度きりイベントの再発・デッドエンド・ゲームオーバー分岐・クリア到達可否までスモークプレイで確認してください。なお生成 JSON 先頭に BOM が付くため、`Story` へ渡す前に除去します（`readFileSync(...,"utf-8").replace(/^﻿/, "")`）。
